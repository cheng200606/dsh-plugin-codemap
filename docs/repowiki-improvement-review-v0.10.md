## 1. 本次修复与重构

### 1.1 图谱拖拽：根因与修复

**根因**：图谱 SVG 只绑定了 `wheel`（原生非被动监听）和节点 `click`，没有任何 `pointerdown/pointermove/pointerup` 处理；`viewBox` 只能被滚轮/按钮修改，所以鼠标左键拖动完全没有效果。

**修复**（`client.js` `graphView()`）：

| 能力 | 实现 |
|---|---|
| 左键平移 | `pointerdown` 记录起点、当前 viewBox、屏幕→SVG 比例；`pointermove` 反算 `x/y` |
| 拖拽阈值 | 位移 < 3px 视为点击，避免“手抖”取消选中 |
| 指针捕获 | 首次真正移动时才 `setPointerCapture`，保证普通点击仍能命中节点 |
| 点击抑制 | 拖拽结束后只抑制本次手势的 `click`；下一次 `pointerdown` 自动复位 |
| 双击适配 | `dblclick` 将 viewBox 重置为 fit-to-content |
| 键盘 | 方向键平移 8% 画布宽度；`+`/`-` 缩放；`0` 重置 |
| 性能 | 布局/走线 `useMemo`；拖拽更新用 `requestAnimationFrame` 合帧；卸载时取消帧与 impact 请求 |
| 无障碍 | SVG 可聚焦；节点 `role=button`、`tabIndex=0`、`Enter/Space` 选中、`aria-pressed` |

**验证**：

## 3. 深挖 Top 5

### 3.1 为什么“确定性模板”是产品天花板，而不是实现细节

当前插件用代码直接算 EvidencePack、渲染模板、校验引用，所以 **0 模型调用、0 token、279 ms 生成 8 页**。这是巨大的成本/可复算优势，但也带来一个硬上限：

- 模板能写“这个模块有哪些文件、被谁引用、暴露了哪些符号”，但写不出“为什么这样分层”“这个取舍的代价是什么”。
- 新功能（`panel.js`、`routes.js`）没有对应的计划页时，正文不会自动出现“面板/侧栏”这些词，搜索自然 0 命中。
- 结果：Wiki 更像“结构化代码索引”，而不是“项目知识”。

**建议的折中**：保留 EvidencePack 作为唯一事实源，新增“叙述层”：
1. 零依赖版：从 JSDoc、路由表、配置键、调用链生成“设计意图候选句”，但仍标注来源；不编造。
2. 可选模型版：只让模型基于 EvidencePack 写“关键结论/实现细节”两节，输出必须带 claim id；校验器逐条核对；模型失败则回退模板。
3. 两者都缓存到页面 `source_hash`，未变不重复生成。

**收益**：在不破坏“引用可验证”的前提下，把 Wiki 从“索引”提升为“可读的知识”；预期新功能相关查询命中率从 0 提升到可度量水平。

### 3.2 图谱缓存与数据新鲜度

- 服务端 `buildRepositoryProfile()` 有 5s TTL + 目录签名；源码变化后，下一次 `/graph` 会重新索引。
- 客户端 `graphData` 没有 TTL，只在 `generate()` 成功、切换 root、重新进入 `graph` 且 `!graphData` 时清空。
- 因此：**服务端是新鲜的，客户端可能是旧的**。

**建议**：
1. `/graph` 响应增加 `head`/`signature`/`generatedAt`。
2. 客户端保存 `graphSignature`；每次进入图谱或每 30s 比对，不一致显示“数据可能过期”并启用刷新按钮（按钮已存在）。
3. 生成完成后递增一个 `wikiVersion`，图谱/面板/搜索共用失效。

**收益**：消除“看起来最新、实际旧图”的信任问题；实现成本低（S）。

### 3.3 `root` 信任边界

`resolveRequestRoot(explicit)` 的逻辑是“显式 root 只要 `isDirectory` 就接受”。这带来两个问题：

1. 任意已存在目录都能成为 Wiki 根，随后 `/api/repowiki/export` 可在该目录写 `.qoder/repowiki`，`/panel` 可读该目录的 `.dsh/repowiki`。
2. Web 路由没有 agent/session，无法用“用户当前工作区”做天然约束；只能依赖 token 栅栏与同源策略。

**建议**：
- 显式 root 必须在 `workspaceRoots()` / `sessionRoots()` / `lastRoot` 的白名单内；
- 其他目录要求 `confirm=1` 或一次性授权，并记录到 `runtime.json`；
- `export` 目标路径必须在 root 内，且导出前备份。

**收益**：把“本地便利”限制在可信工作区；消除越权读写类问题。

### 3.4 大图性能

当前优化：
- `graphScene` 用 `useMemo` 只在 `graphData` 变化时重算布局/走线；
- 拖拽用 `requestAnimationFrame` 合帧；
- 节点上限 300，超出截断。

仍不够：
- React 每次 pan 仍 diff 300 个 `<g>` + 边；
- 所有节点/边都在 DOM 中，无视口裁剪；
- 文本节点在 SVG 中较重。

**建议**：
1. 先加基准：300 节点下连续拖拽 2s，统计 `requestAnimationFrame` 间隔与长任务。
2. 若平均帧 > 16ms：改为“拖拽期间只改 `<g transform>`，pointerup 再提交 viewBox”；或对视口外节点用 `display:none`。
3. >800 节点：切换 canvas/WebGL 渲染，或只渲染当前层 + 相邻层。

**收益**：保证 2 万文件压测下仍可交互；避免“功能有了但一拖就卡”。

### 3.5 单文件客户端与测试缺口

`client.js` 3 646 行，包含：
- 词典、CSS、图标、基础组件、Markdown 渲染、图谱布局/走线、面板状态机、请求封装、路由交互、五态视图。

风险：
- 任何小改动都可能影响无关视图；
- 没有 DOM 级测试，只有宿主自检 10 项 + 服务端 30 项；
- 视觉回归靠人眼截图。

**建议**：
1. 先 `git init` + 基线提交（P0）。
2. 把 `client.js` 拆为 5–6 个源文件，用 Node 内置脚本拼接；保持“零依赖、无构建”的安装体验。
3. 加 Playwright 视觉基线（明/暗 × 图谱/阅读/卡片）+ 交互断言（拖拽/缩放/节点选择/键盘）。
4. 把本次的 `probe2.js`/`probe3.js` 收敛为 `test/ui-e2e.mjs`，纳入回归。

**收益**：把“这次修好了”变成“以后不会坏”；降低后续 UI 迭代风险。

## 6. 结论

这次交付解决了用户直接感知的两个问题：**图谱不能拖**与**界面不够精致**。但从代码审查看，插件已经从“最小可用”进入“需要工程化”的阶段：

- **不要再加视图**，先把版本控制、信任边界、缓存与测试补齐；
- **不要再靠模板堆内容**，把“叙述层”作为下一个产品杠杆；
- **不要继续用手眼验证 UI**，把 Playwright 截图/交互断言纳入回归。

按本文 P0 → P1 顺序推进，插件才能从“能演示”走到“可长期维护”。
